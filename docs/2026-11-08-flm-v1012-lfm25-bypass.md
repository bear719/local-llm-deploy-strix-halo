## 五、验收实测

### 5.1 NPU 功能验收（21:44）

| # | 用例 | 结果 |
|---|---|---|
| ① | 中文医疗文本分类 + 三字段显式关闭 | `{"label": "医疗"}`，wall 0.744 s，TTFT **0.490 s**，decode **45.5 t/s** |
| ② | 同 system 第 2 轮（prefix cache） | TTFT 0.493 s，`cached_tokens=81`，`lookup=hit`，`miss_reason=None`，`slots_used=6` |
| ③ | `response_format={"type":"json_object"}` | 输出 `{"label": "医疗"}`，decode 39.0 t/s |
| ④ | 未知字段 `this_field_does_not_exist` | **HTTP 200，被静默忽略**（与文档一致） |

- **JSON 合法率 4/4 = 100%**，无思考链残留。
- `think:false` / `presence_penalty:0` / `temperature:0` 三字段按条显式发送，符合「FLM 采样字段粘滞」的约束。
- 短请求 decode 39–45.5 t/s 受固定开销影响（生成仅 3–4 token）；官方 LFM2.5 Strix 组为 56→45，本机 `balanced` 档落在区间内。

### 5.2 三组 A/B：NPU 占空比对 8080 decode 的影响

统一口径：`timings.predicted_per_second`（服务端自报 decode 速度，非 wall 含 prefill）；每请求带随机 `uuid` 前缀规避 LCP 缓存；`max_tokens=200`。

| 场景 | 采样 | GPU decode 中位 | 相对基线 |
|---|---:|---:|---:|
| **NPU 空闲**（基线） | 9 次 | **76.3 t/s** | — |
| **NPU 低频旁路**（每 4 s 一条，占空比 17%） | 4 次 | **75.30 t/s** | **−1.5%** |
| **NPU 满负荷持续压测**（无限循环） | 5 次 | **64.95 t/s** | **−12.7%** |

明细：

```
基线        : 76.14, 75.43 | 76.64, 76.06, 77.00, 76.26 | 74.44(前测)
低频 17%    : 76.51, 73.06, 74.93, 75.67
满负荷      : 70.54, 67.96, 64.95, 62.03, 61.63   ← 单调下滑
```

**关键判读**：

1. **对照组排除了热漂移**。单独连跑 6 次 GPU（全程不起 NPU）：`73.9 → 75.4 → 76.9 → 74.5 → 74.4 → 75.9`，**无下降趋势（+2.8%）**。证明满负荷组的 70.5→61.6 单调下滑由 NPU 造成，不是机器热了。
2. **满负荷组呈渐进式挤压**，而非一次性阶跃：NPU 持续满载约 10 s 后 GPU decode 才跌到 62 t/s，说明是 120 W 功耗预算与 UMA 带宽被逐步抢占。
3. **低频组完全达标**：17% 占空比下 −1.5%，远好于 3% 门槛。真实旁路（分类/路由/OCR/embedding）的调用密度远低于「每 4 秒一条」，因此生产风险可接受。
4. **prefill 几乎不受影响**：交错实验中 A/B 的 `prompt_per_second` 为 261/257、257/258、244/265，差异在噪声内。争用主要体现在 decode（带宽密集）。
5. −12.7% 与社区 `1bit-MONSTER` 的「GPU busy 时 NPU 保留 ~87% 带宽」互为镜像，量级吻合（本机 13% ≈ 其 13%），首次在本机把该数字实测出来。

### 11.2 启动脚本里的关键写法（回滚口径）

```bash
# ★ 刻意用 ${VAR-默认}（单横线），不是 ${VAR:-默认}
NPU_UPSTREAM="${NPU_UPSTREAM-http://127.0.0.1:8219}"
NPU_MODEL_TAG="${NPU_MODEL_TAG-lfm2.5-it:1.2b}"
NPU_MIN_MEMAVAIL_MIB="${NPU_MIN_MEMAVAIL_MIB-4096}"
```

差异是实质性的，已实测三种情形：

| 情形 | `${VAR-默认}`（本方案） | `${VAR:-默认}`（错误写法） |
|---|---|---|
| 变量未设置 | 取默认值 `http://127.0.0.1:8219` | 取默认值 |
| **变量显式设为空串** | **保持空 → 分流关闭** | **被替换成默认值 → 无法关闭** |
| 变量设为别的地址 | 保留用户值 | 保留用户值 |

用 `:-` 会导致「清空变量来关旁路」这个最常用的回滚手段失效，必须用 `-`。

## 八、回滚方案

| 层级 | 操作 | 影响 |
|---|---|---|
| L1 停分流（最轻） | 把 `NPU_UPSTREAM` **设为空串** → 重启 18090 | 秒级，代码不动，流量全部回 8080 |
| L2 停旁路 | 面板停止 `flm-npu-8219` | 秒级；若 `NPU_UPSTREAM` 仍指向 8219，NPU 请求会 502（**不会**回落 8080） |
| L3 退补丁 | `python3 tools/apply-npu-route.py --revert` → 重启 18090 | 从 `tools/docproxy.py.bak.20261108-npu` 原样恢复 707 行版本 |
| L4 降版本 | `sudo apt install ./backup/.../fastflowlm_1.0.12_*.deb` 的反向：取 v0.9.45 deb 重装 + 恢复 `model_list.json.v0.9.45` | 需重取旧包；旧权重目录仍在盘 |
| L5 卸模型 | `rm -rf $HOME/models/flm/models/LFM2.5-1.2B-NPU2` | 释放 959 MB |

**回滚优先级**：优先 L1 —— 只改一个环境变量，零代码风险。**切勿**先动 L3，除非 L1 无效。

**注意**：v1.0.x 已让旧 `Qwen3.5-4B-NPU2` 权重失效（v1.0.2/1.0.3 起要求重下），若要回到 4B 必须重新 pull，不能指望 4.7 GB 旧目录直接可用。

## 九、口径订正（覆盖前序报告）

1. **「NPU 并发对 GPU 无影响」不成立**。真实数字：低频 −1.5%，满负荷 −12.7%。此前「−13% 折损 [UNVERIFIED]」现已在**本机实测证实**，可去掉 UNVERIFIED 标记。
2. **「先跑 A 组再跑 B 组」的分组 A/B 是错的**。首轮分组测试得到 `+374.5%` 的荒谬结论，根因是 A 组头两次撞上 8080 冷态爬坡（3.34 → 9.48 → 50.76 t/s），B 组全程热态。改为「预热丢弃 + 交错执行 + 服务端自报 timings」后才得到稳定数据。**该教训适用于后续所有主链路压测。**
3. **本机 8080 当前基线是 ~76 t/s，不是 90.14 t/s**。原因是权重已从 `Q4_K_P` 换成 `Q5_K_P`（`Qwen3.6-35B-A3B-Uncensored-Q5_K_P.gguf`，显存 43.7 GB），且 `--spec-draft-n-max` 等参数可能不同。**引用 90.14 时必须注明那是对应 Q4_K_P 的旧基线。**
4. **`flm pull` 不吃 `HF_ENDPOINT`**。国内拉模型只能靠 `--modelscope 1`（且需先清 `.part` 残留），不能用 `hf-mirror` 环境变量。
