# 2026-11-23 NPU 充分利用方案（不限于本地模型推理）

> 调研与实测日期：2026-11-23 09:54–10:00
> 现役实例：`flm serve hy-mt2-flash:1.8b --port 8219 --embed embed-gemma:300m --asr whisper-v3:turbo`（PID 12897，root，面板托管）
> 本文所有数字均来自本机当日实测，未实测项明确标注 `[待实测]`。

---

## 0. 一句话结论

**NPU 的稀缺性在「不占 VRAM、不抢主 slot、<2 W 常驻」；它的瓶颈在「全局串行 + 小模型带宽墙」。**
因此唯一正确的用法是：**把 NPU 变成平台的「离线批处理工人 + 常驻小能力端点」**，
而不是「让大模型变快」。后者（NPU 分摊 prefill、NPU 跑 35B、NPU 做 judge）本机已逐项实测否决。

## 2. 已实测能力矩阵（2026-11-23 复测）

| 能力 | 实测 | 结论 |
|---|---|---|
| Embedding（768 维） | 6 条 **1.60 s**（3.8 条/s），768/768 非零 | ✅ **可用，首选** |
| 语义检索 Top-1 | 4 条查询 **4/4 命中**（抑酸药 / 过敏 / 门脉高压 / 饮食） | ✅ 质量够病案检索 |
| 中英互译 | 23 token → **0.40 s**；中→英 0.87 s；英→中长句 0.90 s | ✅ **专用 MT 模型强于 35B** |
| JSON Schema 约束抽取 | `hy-mt2-flash` 抽取「奥美拉唑 40mg 静推 q12h」→ **0.93 s**，字段全对 | ✅ 格式由 xgrammar 保证 |
| 分类（枚举约束） | 5 条病历行 **0.45–0.56 s/条**，总 2.48 s | ⚠️ **格式对，语义错**（「血常规」判为「其他」） |
| 纠错生成 | `hy-mt2-flash` **原样返回**（0 处修正）；`qwen3-it:4b` 需 6.01 s 且「少傅」→「少腹」（错） | ❌ **否决** |
| A/B 句子判别 | 「乙型肝炎 vs 乙型感炎」正反互置给相反答案 | ❌ **否决**（判断力不足） |
| ASR（中文） | 拼音层确定性纠错后 CER 4.11% | ✅ 已上线 |

**★ 决定性物理量：有效带宽**

| 引擎 | 参数读取 | decode | 有效带宽 |
|---|---:|---:|---:|
| NPU `hy-mt2-flash:1.8b` | 3.0 GB | 52.3 t/s | **57.4 GB/s** |
| NPU `qwen3-it:4b` | 3.1 GB | 22.0 t/s | **140.9 GB/s** |
| iGPU 35B-A3B Q5_K_P | 2.751 GB/token | 76.3 t/s | **209.9 GB/s** |

→ **NPU 的内存带宽只有 iGPU 的 27%（1.8B 档）～67%（4B 档）**。
这就是「NPU 跑什么模型都慢」的根因，与模型大小无关：**小模型吃亏在带宽，大模型吃亏在带宽 + 容量**。
推论：**任何对延迟敏感或需长生成的活都不该给 NPU**；只该给它「小输出、可延迟」的活。

## 3. 已被否决的方向（勿再投入）

| 方向 | 否决依据 |
|---|---|
| NPU 跑 35B-A3B 当主模型 | 12.11 t/s @1k，TTFT 10.8 s，且本机 host 30.47 GiB 必 OOM |
| NPU 分摊 GPU prefill | `1bit-MONSTER` 实测 loss；`gufo serve` 分块永不满足 `n_tokens%4096==0` → serve 下 NPU 触发 0 次 |
| NPU 做 judge（难度判定） | 35B 20/20 @0.63 s vs 1.2B 11/20 @0.68 s |
| NPU 做病历纠错判别 | 本日实测：位置偏置 + 无纠错能力 |
| NPU 做 freeform 分类 | 本日实测：格式对、语义错（「血常规」→「其他」） |
| 神经网络风格自定义算子（ONNX / 自写 kernel） | `/usr/include/xrt` 缺失，需要 xrt dev + `xclbin` 编译链；Vitis AI / IRON 工具链未装，收益远低于成本 |

## 4. 候选方向全景（按可落地性排序）

### 4.1 ⭐⭐⭐ 常驻小能力端点（Already Running，只需固化调用）

现役实例已经同时挂了 chat(MT) + embed + ASR，**但只有 docproxy 分流在用**。可立即落地的四类消费方：

1. **Embedding 语义检索底座**（最强项）
   - 病案库 / 指南库 / 论文库分块 → 向量 → 本地索引。
   - 吞吐 3.8 条/s ⇒ 1000 页病案（约 4000 块）**≈ 17.5 分钟**；建议挂夜间 cron + GPU 空闲门控。
   - 检索质量：4/4 Top-1，可直接替代「关键词 grep」。
2. **医学翻译**（`hy-mt2-flash:1.8b` 定稿）
   - 与 35B 对比：同一句 0.40 s vs 9.48 s（**快 23.7×**），术语准确率持平。
   - 消费方：阅读英文指南 / 写英文摘要 / 表格字段双语化 / 代码注释。
3. **ASR**（`whisper-v3:turbo` + `pyfix.py`）
   - 会议记录、讲座录音、门诊口述草稿；**不可用于正式病历**（残余 CER 4.11%）。
4. **结构化抽取**（json_schema 强制）
   - 只做「schema 明确的字段搬运」，不做语义判断。例：药品行 → `{药名,剂量,途径,频次}`。

### 4.2 ⭐⭐⭐ 离线批处理工厂（NPU 真正的价值洼地）

NPU 的定位应是「**第二台引擎**」而非「加速器」：GPU 跑交互（76.3 t/s），NPU 跑吞吐（3.8 块/s）。
只要任务满足「**可延迟 + 无生成 + 大批量**」，NPU 就是免费的。

| 批处理任务 | 单条耗时 | 规模估算 | 推荐时段 |
|---|---:|---|---|
| 文档/病案向量化 | 0.26 s | 1000 页 ≈ 17.5 min | 夜间 |
| 批量翻译（中英对照语料） | 0.4–0.9 s | 100 段 ≈ 1 min | 任意（占空比低） |
| 批量字段抽取 | 0.9 s | 500 行 ≈ 7.5 min | 夜间 |
| 音频转写 | 3.3–5.4× 实时 | 1 h 录音 ≈ 15 min | 线下 |

**★ 必须配 GPU 空闲门控**：满载 NPU 会让 GPU decode 掉 12.7%。
本日已交付 `tools/npu-idle-gate.py`（读 8080 `/slots` + `MemAvailable`，连续空闲 N 秒才放行）。

### 4.3 ⭐⭐ d3 Decision 档位（已下载 D3-Edge，未启用）

`d3:edge`（596 MB）= Qwen3.5-0.8B 编码器 + 255 类动作码 readout，`POST /v1/systemone` 返回概率。
**它不生成文本、不含难度维度**，只适合「工具/路由选择」这类只取决于 prompt 词面的决策。

- 可用场景：`docproxy` 里「这条请求该走哪个后端」的极速初判（**必须带规则兜底**）。
- 不可用场景：判定请求难度、判定内容质量（judge 已否决）。
- 代价：`/v1/systemone` 是 flm 私有端点，docproxy 现有补丁不认，需新增路由分支。
- 风险：NPU 全局串行 —— 高并发命中 d3 时，会挤占 embed/ASR 队列（实测 146 ms → 12.7 s）。

### 4.4 ⭐⭐ 量化/模型转换的「独立验证机」

同一个模型在 NPU（`.q4nx`）与 GPU（GGUF）双后端跑同一批 prompt，
用输出一致性做**量化无损性抽检**，且不占用 GPU 显存。
`[待实测]` 目前无同权重双格式模型，需先确认 flm 仓库是否有 Qwen3-4B 的 `.q4nx` + 对应 GGUF。
价值：替代「靠人眼看几个例子」的粗糙验收。**不值得专门投入**，顺手做即可。

### 4.5 ⭐ 系统侧「不占 GPU 的常驻计算」

| 想法 | 判定 |
|---|---|
| 本地 TTS / 语音合成 | ❌ flm 无 TTS；NPU 接入需自研 kernel。现用 Breeze-TTS-2（Vulkan）已够 |
| 本机常驻语音助手（唤醒词 + ASR + 1.2B 回复） | ⚠️ 技术可行（whisper + lfm2.5），但 1.2B 回复质量不足，且与主链路串行冲突。仅作玩具 |
| 摄像头/屏幕 OCR | ❌ `qwen3vl-flash:4b` 图片长边缩到 256 px，OCR 不可用 |
| 后台日志异常检测 | ⚠️ 可做 embedding 聚类，但价值低于直接 `grep` |
| 密码/密钥本地处理 | ❌ 无意义，NPU 不是安全域 |
| 挖矿 / 通用算力出租 | ❌ 无 XDNA2 通用算力池生态 |

### 4.6 ⭐ 自研 NPU 算子（高成本，明确不推荐）

要跑非 flm 支持的模型（如自定义 ASR、视觉模型），路径是：
`XRT + xclbin（Vitis AI / IRON / mlir-aie 编译）` → **本机缺 `/usr/include/xrt`**，需装 `xrt-dev` 并确认 amdxdna 7.0 兼容。
实测数据说明这条路的性价比：即便跑通，带宽上限 57–141 GB/s，**永远慢于 iGPU**。
→ **只在出现「flm 完全没有、且必须低功耗常驻」的刚需时再考虑**。

## 5. 推荐落地路线（三步，按收益/成本排序）

### 第 1 步：把 embedding 变成基础设施（收益最高，0 新增依赖）

```
文档 → 分块（512 字 / 重叠 64）→ npu-sidecar.py embed → idx.jsonl
查询 → npu-sidecar.py search idx.jsonl "问题" --topk 5
```

- 已交付工具：`tools/npu-sidecar.py`（embed / search / translate / extract 四子命令，纯标准库）。
- 建议数据：`~/WorkBuddy/调试本地模型/*.md`（70+ 篇实验报告）+ 医学指南 PDF 转文本。
- 门控：`npu-idle-gate.py --wait 1800 && npu-sidecar.py embed ...`

### 第 2 步：翻译/ASR 消费方接入（改一行环境变量）

docproxy 已具备分流（`NPU_MODEL_ALIASES` 含 `hy-mt2-flash:1.8b`），客户端只需 `model=hy-mt2-flash:1.8b`。
待办：把「读英文指南」的本地脚本默认模型从 35B 改成 NPU MT（快 23.7×）。

### 第 3 步（可选）：d3 路由实验

在 docproxy 增加 `X-Backend: d3` 分支 → `/v1/systemone`，用 200 条真实请求对比「d3 判定 vs 35B judge」的路由正确率。
**验收门槛：正确率 ≥ 95% 才上线**，否则维持现状。

## 6. 红线（不可越）

1. **NPU 全局串行**：任何场景都不得并发压测 8219；批量任务必须排 GPU 空闲窗口。
2. **满载代价 12.7%**：NPU 满负荷时 GPU decode 76.3 → 64.95 t/s。低频 17% 占空比只掉 1.5%。
3. **不碰 96 GiB UMA**：改 BIOS 上大 GTT 引擎（Gufo/Strata/Halogen）会把 NPU 一起关掉（`amd_iommu=off`）。
4. **8219 无认证 + 绑 0.0.0.0**：局域网可访问。收敛方案：`HOST=127.0.0.1` 后重启面板实例（docproxy 同机走回环不受影响）。
5. **`think` / `presence_penalty` 粘滞**：跨客户端共享，每条请求必须显式发 `think:false` + `presence_penalty:0` + `temperature:0`。
6. **结构化输出必须用 `json_schema`**：格式可强制，判断力不可强制 —— 该靠规则的地方别指望模型。
