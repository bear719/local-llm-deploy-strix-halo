# 出片流程自检报告：把「诊断」也做成流水线的一环

来源：本机出片工作台的流程优化报告（`optimize`），2026-11-22 21:07 (GMT+8)。
报告由本地大模型基于确定性采集的证据生成，全程只读、不改任何生产文件。

本篇抽掉一次性编号与项目路径，只留**可复用的采集字段、判据与「本地模型做诊断」的边界**。

---

## 一、这套自检的思路

出片管线跑不顺时，最贵的不是算力，是**人来回猜**。所以把「采集 → 诊断 → 建议」做成一键流水线：

```
采集固定字段（配置 / git / 事件日志 / 依赖服务健康）
   ↓
喂给本地大模型（结构化摘要，不给原始日志）
   ↓
产出「问题 / 证据 / 影响 / 动作 / 成本 / 风险」六列表
   ↓
人工挑一行执行，改完跑一集回归
```

**关键设计：本地模型只做归纳，不做结论担保。** 每个结论必须挂一条可回查的证据（配置键、日志 pattern、git 计数），没有证据的结论一律丢弃。

---

## 二、固定采集字段（可照抄）

| 分组 | 字段 | 用途 |
|---|---|---|
| 版本 | git 分支 / HEAD / 未提交改动文件数 / 最近提交 | 判断「跑的到底是哪份代码」 |
| 参数 | 后端、步数、并发、分辨率、帧率、单镜时长、采样器 | 参数漂移的第一现场 |
| 事件 | 近 N 天事件数、完成集数/镜头数、错误事件占比 | 判断「是没跑，还是跑挂了」 |
| 日志 | `api.log` 疑似错误行数 + top-N 错误 pattern 及计数 | 定位高频故障（端口占用、超时） |
| 服务 | 本地推理 8080 / 代理 18090 健康 | 应用链路是否通 |

> 采集与诊断**必须分离**：采集是确定性的（固定命令、固定解析），诊断才交给模型。把采集也交给模型，等于让模型编数字。

## 三、本次诊断的四条结论与它们的真实价值

| 结论 | 证据 | 落地判断 |
|---|---|---|
| 渲染并发 = 1，GPU 利用率低 | `render.concurrency=1` | **表面正确的坏建议** —— 本机 96 GiB 单池、每段重载约 40 GiB 权重，并发 >1 会直接触发 `ErrorDeviceLost`（详见 `../director-console/02-gpu-arbiter.md`）。模型不知道这条约束 |
| API 端口绑定冲突 | `api_log.error_top[0]`：`address already in use` ×10 | ✅ 真问题，`ss -ltnp` 查占用后重启即可 |
| LLM 深度审查超时 | `TimeoutError` ×3 | ✅ 真问题，多半是审查时槽位被渲染/另一请求占用 |
| 未提交改动 147 个文件 | `git status` 计数 | ✅ 真问题 —— 出事时无法复现 |

**结论：4 条里 3 条可用，1 条必须由人否决。**

这正是本地模型做诊断的正确用法：**它是归纳器，不是领域专家**。凡是涉及「本机硬件约束」的建议，必须过一遍人工的领域规则。

---

## 四、把「模型不知道的约束」写成硬规则

模型会重复给出同一类错误建议。解法不是反复纠正它，而是把这些约束**写成检查项**，让它没机会出现在建议列表里：

| 约束 | 写成什么 |
|---|---|
| 单池 96 GiB、并发必须 = 1 | 采集字段里直接附 `concurrency_max=1` 与理由，模型读得到就不会建议提并发 |
| `-ngl 999` 下 MoE 缓存被禁用 | 参数检查项：`moe_cache` 与 `ngl` 同时出现 → 标记 `disabled_by_design` |
| `steps=12` 属 draft 档 | 参数检查项直接标注档位名，避免「12 步太快了」这类伪问题 |
| 8080 不通可能是仲裁器暂停 | 事件采集带上「是否有渲染进程」，否则会误判为崩溃 |

> 通用做法：**把「为什么不能这么做」写进采集数据的上下文**，比事后在 prompt 里追加一句「注意不要…….」有效得多。模型的建议质量，取决于输入里有多少显式约束。

---

## 五、报告产物应当具备的形状

一份能直接执行的自检报告，至少三段：

1. **证据表**：每条结论后面跟键名 / pattern / 计数（可回查，不接受叙述性描述）；
2. **按收益/成本排序的建议表**：成本用 S/M/L，风险用低/中/高，禁止只给「建议优化」这种空话；
3. **回滚与回归**：每条改动怎么撤、改完跑什么验证（本管线是「跑一集回归」）。

缺第 3 段的报告，等于把风险转嫁给执行者。

---

## 六、这套做法的边界

| 适用 | 不适用 |
|---|---|
| 归纳大量结构化指标、抓高频日志 pattern | 判断硬件/显存类约束（模型看不到现场） |
| 把散落证据整理成可读表 | 决定创作取向（拆不拆长镜、要不要丢字） |
| 生成「下一步命令」草稿 | 直接改生产文件（必须隔离，只读采集） |
