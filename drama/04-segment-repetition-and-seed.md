# 04 · 单镜内分段重复：判重、根因与三条路线

一个镜头超过单段帧数上限就要拆成多段。拆完之后出现了诡异现象：
**后一段不是接着前一段末尾演，而是倒回起点重演了一遍。**

本篇记录：怎么量化它、三条叠加的根因、以及三条可选路线怎么取舍。

---

## 一、先量化：到底怎么个「重复」法

### 1.1 判重指标：用 MAD，不要用 MSE

```
MAD = 逐像素绝对差的均值（0–255 标度）
MSE = 逐像素平方差的均值
```

视频里的小幅动作在 MSE 下被平方压到 `0.003`，看起来像「完全冻结」，
会得出完全错误的结论。

> **实测对照：同一对帧 MSE = 0.003 ⇔ MAD = 0.64 / 255。**
> 一旦用 MSE 当阈值，任何微小运动都会被误判成「重演」。

### 1.2 判重演的铁律

> **若 B 段的每帧与 A 段同序号帧的差异 < A 段自身首末帧的变化量，则 B 逐帧复制了 A。**

三个量要同时看：

| 量 | 含义 | 重演时表现 |
|---|---|---|
| `B首帧 \| A尾帧` | 接缝是否连上 | ≈ `A 段内总变化`（等于说 B 回到了 A 的起点） |
| `A 段内总变化` | A 从首帧到尾帧动了多少 | 基准 |
| `B首帧 \| A首帧` | B 是不是从 A 的起点开始 | **极小** |

### 1.3 实测结果

产物 768×1344 @ 24 fps，每段 39 帧 / 1.63 s：

| 镜头 | 段对 | 重演率 | 接缝 B0\|A尾 | A 段内总变化 | B0\|A0 | 判定 |
|---|---|---|---|---|---|---|
| SHOT-001 | s00 → s01 | **1.000** | 35.34 | 34.46 | **7.05** | **重演** |
| SHOT-001 | s01 → s02 | 0.103 | 9.19 | 35.60 | 32.70 | 正常续演 |
| SHOT-002 | s00 → s01 | **0.718** | 15.70 | 15.98 | **4.92** | **重演** |

**读法**：重演的那一对，`接缝B0|A尾` ≈ `A段内总变化`（35.34≈34.46，15.70≈15.98），
而 `B0|A0` 极小（7.05 / 4.92）—— 说明新段**倒回起点重演**。
`replay_ratio ≈ 1.0` 意味着两段逐帧同轨迹（lockstep）。

**规律**：重演集中爆发在 **第 1 → 第 2 段**；第 2 → 第 3 段正常。

## 二、三条叠加的根因

### 根因 1 ★：H3 走的是 Ref2VA —— 参考图是「参考」不是「锁帧」

`-r/--ref-image`（包括把上一段尾帧当参考图）**不硬锁首帧**，
模型可以自由选择从动作开头起演。

社区明确区分两种模式：

| 模式 | 含义 | 是否锁帧 |
|---|---|---|
| **Ref2VA** | 用参考图描述角色外观（身份锚定） | **不锁帧** |
| **FL2VA / I2VA** | 用一帧作为镜头锚点 | **锁帧** |

### 根因 2 ★★★：`sd-cli` 的 `--seed` 默认是 42

不传 `-s` 时，**全片每镜每段用同一个种子**。

三层证据：

1. 实际命令行（`.sdcli.log` 首行）里**没有 `-s`/`--seed`**
2. 源码 `examples/common/common.h:209` → `int64_t seed = 42;`
   帮助文本原文：`RNG seed (default: 42, use random seed for < 0)`
3. 源码 `examples/common/common.cpp:2827` → `params.seed = seed;` **无条件赋值**
   （覆盖了 `sd_vid_gen_params_init()` 里设的 `-1`）

→ 同种子 + 同参考图 + 同提示词前缀（动作未按段拆时）= **同一条去噪轨迹** = 重演。

> ★ **坑中坑**：workflow JSON 里的 `noise_seed`（例如 `586748227622559`）
> 在 sdcpp 后端下**完全无效** —— 真正决定种子的是 CLI 的 42。
> 改 workflow json 调种子是白费功夫。
>
> ★ 社区里「所有分段共用同一种子」是给 **latent 续接**用的 —— 那里连贯性来自 latent，
> 同种子是必要的。我们走的是「各自独立生成 + 参考图」，**同种子只会放大重复**。

### 根因 3：动作未按段拆分

原实现只拆台词、不拆「画面动作」→ 各段拿到同一句动作描述。

修法：按权重分桶拆分动作，且子句不足段数时用**互不相同**的措辞
（「起势 / 继续推进 / 收势」），避免所有段共用同一句。

## 三、sd-cli 原生就有的能力（不必上 ComfyUI）

这是本次调研最重要的发现：社区长视频方案的核心机制，本机 `sd-cli` **原生全有**。

| 能力 | 命令行 | 源码位置 | 对应社区做法 |
|---|---|---|---|
| 参考**视频**（帧目录，按文件名排序，24 fps） | `--ref-video <dir>` | `examples/cli/main.cpp:803-820` | 「固定 Guide / 重叠生成」的原生入口 |
| 参考视频配对音轨 | `--ref-video-audio <wav>` | 同上 | 音轨随画面交接 |
| 独立参考音频（可多次） | `--ref-audio <wav>` | `examples/common/common.cpp:1539` | 口型/音色锚定 |
| **首帧硬锁**（I2VA） | `-i/--init-img <png>` | `src/pipeline/video.cpp:474, 717` | 「仅固定边界」 |
| **首尾帧硬锁**（FL2VA） | `--end-img <png>` | `src/pipeline/video.cpp:480, 717-721` | 关键帧之间的插值 |

模式判定（`video.cpp:717`）：

```
start && end → "MiniMax-H3 FL2VA"
start only   → "MiniMax-H3 I2VA"
```

`--ref-video` 帧目录要求：`load_images_from_dir()` 按**文件名字典序**排序，
支持 `.jpg/.jpeg/.png/.bmp/.webp`，**需零填充命名**（`000.png`、`001.png`…）。

### 3.1 ★★ 硬约束（决定一切路线取舍）

```cpp
// src/pipeline/video.cpp:499-505
bool has_references = ref_images_count > 0 || ref_videos_count > 0 || ref_audios_count > 0;
if (has_references && (!start_image.empty() || !end_image.empty())) {
    LOG_ERROR("MiniMax-H3 keyframes and Ref2VA references cannot be used together");
    return std::nullopt;
}
```

**首/尾帧锁定（`--init-img` / `--end-img`）与 Ref2VA 参考（`-r` / `--ref-video` / `--ref-audio`）互斥。**

一句话：**要身份锚定（`-r` 定妆照）就没有首帧硬锁；要首帧硬锁就没有 `-r`。**

## 四、三条路线与取舍

### 立即见效（零架构改动）

**给同镜各段派生不同种子**：`seed = base_seed + si * K`（或直接随机）。
这是重演的放大器，先拆掉它最划算。

```python
# 在 build_command 里显式传 -s
if seed is None:
    seed = base_seed + seg_index * 7919   # 质数步长，避开 17 帧网格的共振
cmd += ["-s", str(seed)]
```

### Route A：Ref2VA + 重叠生成 + 裁剪（保住 `-r` 身份锚定）

社区主流做法，本机可用 `--ref-video` 实现：

1. 每段多生成 O 秒（**O 建议 22 帧 ≈ 0.92 s**，对齐 H3 合法帧网格 5+17k）
2. 把上一段末尾 O 帧写成零填充帧目录 → `--ref-video`
3. 音频同段 → `--ref-video-audio`
4. 提示词 Shot 1 先描述重叠参考，再写本段新内容
5. 合成阶段剪掉后段重复的重叠帧

| 优点 | 代价 |
|---|---|
| 保住 `-r` 定妆照，身份一致性最好 | 每段多算 O 秒（约 +20~30% 时长） |
| 音轨可随画面连续交接 | 需改 segment / runner / assemble 三处 |

> ⚠ 实测教训：曾用 `--ref-video` 把**解码后的视频**回灌，带来两个问题：
> 逐代质量漂移 + 显存暴涨（+6k token）。
> 社区也明确指出「把 VAE 解码视频回灌 = 逐代质量漂移」，规范做法是传 latent。
> 所以本机用 `--ref-video` 只能用在**相邻段交接**（一次，不递归），不能链式回灌。

### Route B：I2VA 首帧硬锁（连续性最强，放弃 `-r`）

每段 `-i/--init-img = 上一段尾帧`；若关键帧齐全还可 `--end-img = 本镜终点` 做 FL2VA。

| 优点 | 代价 |
|---|---|
| 首帧物理硬锁 → **重演在机制上不可能发生** | 不能用 `-r` 定妆照 |
| 段间严丝合缝 | 不能用 `--ref-audio`（属 references）→ 失去音色锚定 |
| | 段中后段可能脸漂（对 ≤1.63 s 短段风险低） |

**关键洞察**：如果关键帧本来就是用定妆照 img2img 生成的（`kf_strength=0.55`），
**身份信息已经"烘焙"进关键帧** → 不再用 `-r` 也不会立刻脸漂。
这条让 Route B 从一个「牺牲一致性」的方案变成一个「等价」方案。

### Route C：分层（推荐）

| 镜别 | 路线 | 理由 |
|---|---|---|
| 特写 / 近景（身份需求强） | **Route A** | 保 `-r` 定妆照 + 重叠裁剪 |
| 中景 / 全景（身份需求低） | **Route B** | 首帧硬锁，`--init-img` |

正好匹配已经定案的「中景/全景不喂 ref」结论。

## 五、口型不匹配

**现象**：某镜嘴形与台词对不上。

**根因**：该镜**没有传任何 `--ref-audio` 音色参考**，
口型完全由 H3 从提示词里的 `<d>[Chinese] …</d>` 文本自行生成。
叠加「重演」：画面在重演，但每段音频重做 → 音画不同步。

**对策（按优先级）**：

1. **消除重演**（重演时口型也在重演，但音频不会重演）
2. Route A 下用 `--ref-video-audio` 把上一段尾音交接过去，保持音轨连续
3. 检查分段后 `<d>` 对白块是否完整、是否因按字数切分落在**词中间**
   —— 社区规范：**词、句绝不跨段**
4. 走 Route B 时无法用 `--ref-audio`，只能靠提示词把对白文本与说话人写准

## 六、结论速览

| 问题 | 根因 | 首选解法 |
|---|---|---|
| 单镜内分段重复 | ① Ref2VA 不锁首帧 ② 同镜各段同种子（放大器） ③ 动作未按段拆 | 先拆种子；再按 Route A/C 引入重叠裁剪或首帧硬锁 |
| 段间接缝跳回起点 | 新段倒回动作开头重演（接缝 MAD ≈ A 段内总变化） | 同上；Route B 可从机制上杜绝 |
| 嘴形不匹配 | 未传音频参考 + 重演导致口型与重配音不同步 | 消除重演 + `--ref-video-audio` + 校正 `<d>` 切分 |

### 一句话

**种子是第一嫌疑。** 在动任何架构之前，先确认 `-s` 到底传没传 ——
本次排查中，一个默认值 `42` 解释了大部分重演现象。
